# 小药记 / Open Pill Reminder 设计文档

## 1. 文档信息

- 项目名称：小药记 / Open Pill Reminder
- 目标平台：ESP32-C3
- 开发方式：PlatformIO
- 文档版本：v1.0
- 文档日期：2026-04-27

## 2. 项目定位

### 2.1 项目目标

Open Pill Reminder 是一个极简、开源、离线运行的本地服药提醒盒。第一版聚焦以下目标：

- 提供每日重复的本地服药提醒
- 提供用户确认“已吃药”的本地记录
- 提供本地网页控制台进行设置与测试
- 所有配置和记录均保存在设备本地

### 2.2 非医疗声明

本项目不是医疗设备，不提供医疗建议，不用于诊断、治疗、监测或预防疾病。  
本项目仅作为本地提醒和人工确认记录工具。

### 2.3 第一版设计原则

- 本地优先
- 简单可靠
- 易于组装
- 易于维护
- 不依赖云端
- 不引入过多复杂功能

## 3. 第一版功能范围

### 3.1 包含功能

1. 用户可在 Web 页面自由添加每日提醒时间
2. 每天最多支持 8 个提醒时间
3. 每个提醒包含 `id`、`time`、`enabled`
4. 所有提醒按天重复
5. 到点后触发本地蜂鸣器、LED、OLED 提醒
6. 用户按确认键后，记录该提醒已确认和确认时间
7. 未确认时，按 `repeat_interval_minutes` 进行重复提醒
8. 重复提醒次数上限由 `max_repeat_count` 控制
9. 今日记录按日期保存
10. Web 页面支持新增、删除、启用/停用、修改提醒时间
11. Web 页面支持测试蜂鸣器、LED、OLED 和立即触发提醒
12. 所有数据本地保存，不依赖云端

### 3.2 第一版不包含

1. 药品名称管理
2. 剂量管理
3. 按星期选择提醒
4. 云同步
5. 手机 App
6. 用户账号体系
7. 远程消息推送
8. 电池和充电管理
9. 语音播报
10. 多人使用
11. 医疗级日志与合规功能

## 4. 用户场景

### 4.1 基本使用流程

1. 用户接通设备电源
2. 用户通过本地网页进入控制台
3. 用户添加或修改每日提醒时间
4. 到点后设备发出声光提醒并在 OLED 显示提示
5. 用户服药后按下确认键
6. 设备记录“该提醒已确认”和确认时间
7. 如果用户未确认，设备按配置间隔再次提醒，直到达到最大次数

### 4.2 调试流程

1. 用户打开网页控制台
2. 点击测试蜂鸣器
3. 点击测试 LED
4. 点击测试 OLED
5. 点击立即触发提醒，验证整机提醒流程

## 5. 系统总体架构

### 5.1 模块划分

系统分为五层：

1. 硬件驱动层
2. 系统服务层
3. 业务逻辑层
4. Web 接口层
5. 前端页面层

### 5.2 架构说明

#### 硬件驱动层

负责与 OLED、蜂鸣器、LED、按键等外设直接交互。

#### 系统服务层

负责时间获取、存储读写、网络接入、设备状态管理等基础能力。

#### 业务逻辑层

负责提醒调度、状态机推进、重复提醒逻辑、确认记录和每日切日处理。

#### Web 接口层

负责向前端提供本地 HTTP API，处理配置读写和设备测试命令。

#### 前端页面层

负责本地网页控制台展示和交互。

## 6. 硬件方案

### 6.1 核心器件

- 主控：ESP32-C3
- 显示：0.96 寸 I2C OLED，128x64
- 提醒输出：有源蜂鸣器
- 指示输出：1 个 WS2812 或 1 个普通 LED
- 输入：确认按键、设置按键
- 供电：USB-C 5V 输入

### 6.2 最小可行硬件清单

1. ESP32-C3 开发板
2. SSD1306 I2C OLED 模块
3. 有源蜂鸣器模块
4. 轻触按键 2 个
5. WS2812 单颗模块或普通 LED + 限流电阻
6. USB-C 供电接口
7. 面包板或小型打样 PCB

### 6.3 第一版硬件建议

- 优先使用开发板而不是自制核心板
- 优先使用 I2C OLED，减少引脚占用
- 优先使用有源蜂鸣器，降低驱动复杂度
- LED 若以调试和低成本为主，普通 LED 足够
- 若希望状态展示更直观，可使用单颗 WS2812

### 6.4 推荐引脚规划

以下为建议方案，实际需结合开发板可用引脚确认：

- `GPIO4`：I2C SDA
- `GPIO5`：I2C SCL
- `GPIO6`：蜂鸣器
- `GPIO7`：确认按键
- `GPIO8`：设置按键
- `GPIO10`：WS2812 或普通 LED

说明：

- 若使用普通 LED，可改为任意普通 GPIO
- 按键建议上拉输入、按下接地
- 最终引脚需避开启动相关风险脚位和板载占用

## 7. 软件平台选择

### 7.1 选择 PlatformIO 的原因

- 工程结构清晰
- 依赖管理方便
- 便于后续切换开发板
- 便于集成格式化、静态检查和上传文件系统
- 适合开源项目协作

### 7.2 框架建议

第一版建议：

- `PlatformIO + Arduino Framework for ESP32`

原因：

- 上手快
- WebServer、Wi-Fi、文件系统生态成熟
- 适合快速验证产品功能
- 对 OLED、WS2812、按钮、蜂鸣器均有成熟库支持

后续若项目复杂度明显提升，可考虑迁移到 ESP-IDF。

### 7.3 依赖建议

第一版可考虑以下库方向：

- OLED：`Adafruit SSD1306` 或 `U8g2`
- JSON：`ArduinoJson`
- LED：普通 GPIO 或 `Adafruit NeoPixel`
- 文件系统：`LittleFS`
- Web：ESP32 Arduino 自带 `WebServer` 或异步 Web 库

说明：

- 第一版优先稳定，不追求依赖最少
- 若使用异步 Web 库，需要注意后续维护成本

## 8. 功能需求详细定义

### 8.1 提醒配置

每条提醒包含：

- `id`
- `time`
- `enabled`

约束：

- `time` 格式为 `HH:MM`
- 提醒数最多 8 条
- 所有提醒每天重复
- 第一版不支持日期型、星期型、临时型提醒

### 8.2 提醒触发

当设备本地时间到达某条启用提醒的计划时间后：

1. 蜂鸣器发声
2. LED 闪烁
3. OLED 显示提醒界面
4. 等待用户按确认键

### 8.3 确认逻辑

用户按下确认键后：

1. 停止当前声光提醒
2. 记录该提醒今日已确认
3. 保存确认时间
4. 当日该提醒流程结束

### 8.4 重复提醒逻辑

若本轮提醒结束时仍未确认：

1. 进入等待重试状态
2. 经过 `repeat_interval_minutes` 后再次提醒
3. 最多重复 `max_repeat_count` 次
4. 超过最大次数后，记录为未确认结束

### 8.5 Web 控制台

Web 控制台需支持：

1. 查看当前设备时间
2. 查看提醒配置列表
3. 新增提醒
4. 修改提醒时间
5. 删除提醒
6. 启用/停用提醒
7. 修改重复提醒间隔
8. 修改最大重复次数
9. 测试蜂鸣器
10. 测试 LED
11. 测试 OLED
12. 立即触发提醒
13. 查看今日日志

## 9. 数据模型设计

### 9.1 配置数据

#### `DeviceConfig`

```json
{
  "timezone": "Asia/Shanghai",
  "repeat_interval_minutes": 5,
  "max_repeat_count": 3,
  "reminders": []
}
```

字段说明：

- `timezone`：本地时区，第一版可固定为配置项
- `repeat_interval_minutes`：重复提醒间隔，单位分钟
- `max_repeat_count`：最大重复次数
- `reminders`：提醒列表

#### `ReminderConfig`

```json
{
  "id": "r001",
  "time": "08:30",
  "enabled": true
}
```

字段说明：

- `id`：提醒唯一标识
- `time`：每日提醒时间
- `enabled`：是否启用

### 9.2 运行时数据

#### `ReminderRuntime`

```json
{
  "id": "r001",
  "today_date": "2026-04-27",
  "state": "waiting_today",
  "scheduled_ts": 1777249800,
  "alert_started_ts": 0,
  "current_repeat_index": 0,
  "last_alert_ts": 0,
  "confirmed_ts": 0
}
```

字段说明：

- `id`：关联提醒配置
- `today_date`：当前实例所属日期
- `state`：运行状态
- `scheduled_ts`：今日计划触发时间戳
- `alert_started_ts`：本轮提醒开始时间
- `current_repeat_index`：当前重复序号
- `last_alert_ts`：上次提醒时间
- `confirmed_ts`：确认时间戳

### 9.3 每日记录数据

#### `DailyRecord`

```json
{
  "date": "2026-04-27",
  "items": []
}
```

#### `DailyRecordItem`

```json
{
  "reminder_id": "r001",
  "scheduled_time": "08:30",
  "scheduled_ts": 1777249800,
  "status": "confirmed",
  "repeat_count_used": 1,
  "confirmed_ts": 1777249920
}
```

字段说明：

- `reminder_id`：提醒 ID
- `scheduled_time`：计划时间文本
- `scheduled_ts`：该日计划时间戳
- `status`：状态
- `repeat_count_used`：实际使用的重复次数
- `confirmed_ts`：确认时间戳，未确认则为空或 0

### 9.4 状态定义

建议使用以下状态值：

- `disabled`
- `waiting_today`
- `alerting`
- `waiting_repeat`
- `confirmed`
- `expired`

### 9.5 存储方式

建议：

- 配置文件：`/config.json`
- 日志目录：`/records/YYYY-MM-DD.json`

说明：

- 配置单独存储，便于原子替换
- 日志按日期分文件，便于查询与调试

## 10. 状态机设计

### 10.1 状态机目标

状态机用于描述“单条提醒在某一天内”的完整生命周期。

### 10.2 状态说明

#### `disabled`

- 条件：提醒未启用
- 行为：当天不参与调度

#### `waiting_today`

- 条件：提醒启用，等待达到当天计划时间
- 行为：主循环检查当前时间是否到点

#### `alerting`

- 行为：蜂鸣器响、LED 闪、OLED 显示提醒信息
- 等待：用户确认或本轮提醒超时结束

#### `waiting_repeat`

- 条件：本轮未确认，等待下次重复提醒
- 行为：静默等待到达重试时间

#### `confirmed`

- 条件：用户已确认
- 行为：写入记录，当日不再提醒

#### `expired`

- 条件：达到最大重复次数仍未确认
- 行为：写入“未确认结束”记录，当日结束

### 10.3 状态迁移

```text
disabled -> waiting_today
waiting_today -> alerting
alerting -> confirmed
alerting -> waiting_repeat
alerting -> expired
waiting_repeat -> alerting
waiting_repeat -> confirmed
confirmed -> waiting_today (次日重建)
expired -> waiting_today (次日重建)
```

### 10.4 状态迁移规则

1. 开机后加载配置并为当天创建提醒实例
2. 启用提醒进入 `waiting_today`
3. 当前时间达到计划时间后进入 `alerting`
4. 用户按确认键后进入 `confirmed`
5. 若本轮结束未确认，且未超出最大重复次数，则进入 `waiting_repeat`
6. 等待重试间隔到达后重新进入 `alerting`
7. 若已达到最大重复次数则进入 `expired`
8. 日期切换后，为新一天重新建立提醒实例

## 11. 提醒调度设计

### 11.1 调度原则

- 以“分钟级提醒”为目标
- 不追求秒级精度
- 强调稳定可预测

### 11.2 调度策略

主循环周期性执行以下检查：

1. 检查系统时间是否有效
2. 检查日期是否切换
3. 遍历当天全部提醒实例
4. 根据状态和当前时间执行状态迁移

### 11.3 到点判断

当当前本地时间大于等于某提醒的 `scheduled_ts` 时，且当前状态是 `waiting_today`，则进入提醒状态。

### 11.4 重试判断

当当前时间大于等于：

`last_alert_ts + repeat_interval_minutes`

且当前状态为 `waiting_repeat` 时，进入下一轮 `alerting`。

### 11.5 切日处理

当日期从 `YYYY-MM-DD A` 进入 `YYYY-MM-DD B` 时：

1. 将上一日仍未结束的提醒视为 `expired`
2. 写入上一日最终记录
3. 初始化新一天的全部提醒实例

## 12. 本地记录设计

### 12.1 记录目标

第一版记录仅用于：

- 证明设备侧“提醒发生过”
- 记录用户是否完成手动确认
- 记录确认时间

### 12.2 日志内容

每条记录至少应包含：

- 提醒 ID
- 当日计划时间
- 最终状态
- 实际重复次数
- 确认时间

### 12.3 记录时机

建议在以下时机写入或更新：

1. 提醒实例创建时建立占位项
2. 用户确认时更新状态为 `confirmed`
3. 到达最大重复次数后更新状态为 `expired`
4. 日期切换时补齐未结束项

### 12.4 写入策略

建议：

- 先在内存维护今日记录
- 状态变化时写回文件

这样做的优点：

- 避免频繁构造完整对象
- 逻辑更清晰

例如：

- 响 300ms
- 停 700ms

### 17.3 OLED

## 18. 边界情况处理

### 18.1 提醒数量超限

- Web 前端禁止新增
- 固件端保存时再次校验
- 超限请求直接拒绝

### 18.2 重复时间

第一版建议允许重复时间。

处理方式：

- 每条提醒以 `id` 作为唯一实例
- 即使 `time` 相同，也视为两条独立提醒

### 18.3 非法时间格式

- Web 前端校验
- 后端再次校验
- 非法数据不落盘

### 18.4 修改正在运行的提醒

若提醒正处于 `alerting` 或 `waiting_repeat`：

- 修改后立即重算该提醒实例
- 旧计划失效
- 必要时停止当前提醒效果

### 18.5 删除正在提醒的提醒

- 立即停止当前提醒
- 从配置中移除
- 当天记录可记为 `skipped_disabled`，也可不记录

建议：

- 第一版统一记录为 `skipped_disabled`

### 18.6 禁用正在提醒的提醒

- 立即停止提醒
- 当天实例结束
- 记录状态为 `skipped_disabled`

### 18.7 开机时已错过某个提醒

第一版建议：

- 不追补当日已错过的提醒
- 仅处理“当前时间之后”的计划

原因：

- 避免刚开机立即补发多个历史提醒
- 简化用户预期和状态处理

### 18.8 时间不可用

- 不触发正式提醒
- Web 页面显示“时间未就绪”
- OLED 显示错误状态

### 18.9 重复次数为 0

- 仅首次提醒一次
- 不进入重复提醒

### 18.10 重复间隔为 0

- 不允许保存
- 最小值应限制为 1

### 18.11 按键抖动

- 仅首个稳定按下事件有效
- 连续抖动事件应被忽略

### 18.12 断电恢复

- 配置必须可恢复
- 日志文件允许部分丢失，但不能导致系统启动失败

### 18.13 存储写入失败

- API 返回失败信息
- OLED 或串口输出错误提示
- 不应静默失败

### 18.14 跨天时仍在提醒

- 建议在日期切换时将前一天实例封存为 `expired`
- 新一天重新生成计划

## 24. 风险与取舍

### 24.1 第一版主要风险

1. ESP32-C3 资源有限，Web 页面和文件系统需要控制体积
2. 时间同步机制若不稳定，会直接影响提醒可靠性
3. 按键和蜂鸣器的实现细节会影响用户体验

### 24.2 第一版取舍

1. 不做药品维度管理，避免数据模型过早复杂化
2. 不做星期规则，避免调度逻辑扩张
3. 不追补历史错过提醒，降低状态机复杂度
4. 不做云同步，保证离线稳定性

## 26. 实施结论

对第一版而言，推荐采用：

- 硬件：ESP32-C3 + I2C OLED + 有源蜂鸣器 + 2 按键 + 单 LED
- 软件：PlatformIO + Arduino + LittleFS + 本地 Web 控制台
- 数据：JSON 配置 + 按日记录文件
- 逻辑：单提醒实例状态机 + 每日重建调度

该方案具备以下特点：

- 成本低
- 实现快
- 结构清晰
- 适合开源发布
- 适合作为后续扩展版本的基础
